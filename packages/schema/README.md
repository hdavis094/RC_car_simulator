# @rcsim/schema

Every data file the simulator reads or writes, the wiring rules, the car config header generator, and the default parts catalog. It is a **contract**: Phase 1 tasks build against it, and only the orchestrator changes it.

## What is here

| Path | What |
|---|---|
| `src/part-definition.ts` | `PartDefinition`: one kind of part. A discriminated union on `category` (`controller`, `chassis`, `actuator`, `sensor`, `power`, `passive`). |
| `src/behavior.ts` | `Behavior`: the behavior template (`distance-raycast`, `imu`, `servo`, `esc-motor`, `battery`, `voltage-divider`, `regulator`) and its parameters. |
| `src/car.ts` | `Car`: `car.json`, the parts on one car, their pin assignments and placement. |
| `src/world.ts`, `src/track.ts` | `World` (`worlds/*.json`) and `Track` (the built-in tracks, data owned by sim-core). |
| `src/wiring/` | `checkWiring(car, catalog) → Issue[]` and `canRun(issues)`. |
| `src/car-config-header.ts` | `generateCarConfigHeader(car, catalog) → string` (`include/car_config.h`). |
| `catalog/*.json` | The default parts catalog. One file per part, named `<id>.json`. |
| `examples/default-car.json` | The full default car (`exampleCar`) and its generated header `default-car.car_config.h`. |
| `json-schema/*.schema.json` | JSON Schemas for non-TS tools, generated by `pnpm --filter @rcsim/schema generate`. A test fails if they are stale. |

Types are inferred from the Zod schemas, and each schema and its type share a name: `Car` is both the schema value and `z.infer<typeof Car>`. Every file has `schemaVersion: 1`. Objects are strict, so unknown keys (typos) are rejected. Cross-field checks (refinements) exist only in Zod: a file can pass the JSON Schema and still fail `PartDefinition.parse`.

## Conventions

- **Units are in the field names.** Part files use the units datasheets use: `massG`, `dimensionsMm`, `pulseMinUs`, `yawDeg`, `currentMa`. Worlds and tracks use metres: `positionM`. Convert to SI at the edge, in sim-core.
- **Frames.** Right-handed, +Y up, −Z forward. The **chassis frame** has its origin on the ground, midway between the axles and centred left to right. Mount point positions and placement offsets are in the chassis frame, in mm. Yaw is positive turning left, seen from above; pitch is positive tilting up. A placement's yaw and pitch *add* to its mount point's default orientation.
- **Pin kinds are from the part's side.**
  - `digital-in`: the part reads the line, so the controller drives it.
  - `digital-out`, `analog-out`: the part drives the line.
  - `pwm-in`: the part receives PWM.
  - `analog-in`: a divider input.
- **Pin voltage.**
  - A number: the level a pin presents (outputs, power-out) or expects (inputs).
  - `{min, max}`: a varying source, like a battery.
  - `"supply"`: follows whatever the part's power-in pin is connected to.
  - Omitted: the part's `electrical.logicLevelV`.
  - A voltage divider's `OUT` has no voltage of its own: it is `IN × r2 / (r1 + r2)`.
- **Pin assignment.** `car.json` maps each part pin to `{gpio: n}` or `{part: <instanceId>, pin: <name>}`. A wire may be declared from either end. GND is a common ground and never needs listing. Instance ids are lowercase C identifiers, because they become macro prefixes.
- **I²C.** A part's effective address is `i2cAddress ?? i2c.defaultAddress`. Parts using the same SDA and SCL GPIOs share a bus. `addressing` says how the address can change:
  - `fixed`: it can't.
  - `strap`: a pin such as AD0 selects one of a list.
  - `software`: the firmware re-addresses it after holding the others off the bus with `enablePin`, such as XSHUT.

## Wiring rules

Errors block Run in Sim; warnings don't. Issues come out in a fixed order. Each one carries `{severity, rule, message, refs}`, where `refs` point at parts, pins or GPIOs.

| Rule id | Severity | What it catches |
|---|---|---|
| `reference` | error | Unknown part id, pin, GPIO or target part; wrong category in the controller or chassis slot; an I²C address on a part without I²C |
| `pin-kind-mismatch` | error | A wire between incompatible pins, e.g. a power pin on a GPIO, or a signal on a power rail |
| `pin-conflict` | error | A GPIO used twice (shared I²C SDA or SCL lines are fine); two GPIOs wired together |
| `rail-conflict` | error | Two power outputs joined, or a rail shorted to ground or a GPIO |
| `input-only-output` | error | Something the controller must drive, on GPIO 34–39 |
| `flash-pin` | error | GPIO 6–11 |
| `uart0-pin` | error | GPIO 1 or 3 |
| `strapping-pin` | warning | GPIO 0, 2, 5, 12, 15 |
| `no-adc` | error | An analog output on a GPIO without an ADC |
| `adc2-wifi` | error | An analog output on an ADC2-only GPIO while `wifi` is on |
| `level-mismatch` | error | A part driving a GPIO above `gpioMaxInputV` (3.6 V), e.g. a 5 V echo, or a VIN-shifted I²C breakout powered from 5 V |
| `supply-voltage` | error | A rail outside a part's `electrical.supplyV`, or a power pin wired to no source |
| `rail-over-budget` | error / warning | A rail's load over its pin's `maxCurrentMa`: error at typical load, warning when only the peak exceeds it. The load includes downstream rails, through buck efficiency. |
| `i2c-incomplete` | error | Only one of SDA and SCL on a GPIO |
| `i2c-address-invalid` | error | An address the part can't take |
| `i2c-address-unreachable` | error | A software address with no enable pin on a GPIO, or a strap address with the strap pin at the wrong level |
| `i2c-address-clash` | error | Two parts at one address on one bus |
| `unconnected-pin` | warning | A pin that is neither `optional`, nor ground, nor power-out, left open |
| `placement` | error | A sensor without a placement, or a mount point the chassis lacks |

## The car config header

`generateCarConfigHeader` emits the following, wrapped in `CAR_CONFIG_H` guards and a "generated, do not edit" banner:

- `CAR_WIFI_ENABLED`;
- `<INSTANCE>_<PIN>_PIN <gpio>` for every signal pin that reaches a GPIO, directly or through a voltage divider (so `SONAR_ECHO_PIN` is the GPIO behind the echo divider);
- `<INSTANCE>_I2C_ADDR 0x..`;
- `<INSTANCE>_R1_OHM` and `<INSTANCE>_R2_OHM` for dividers.

Names are uppercased; a trailing `+` becomes `_POS` and a trailing `-` becomes `_NEG`. The output depends only on the car and catalog (not on JSON key order), so the same input gives byte-identical text.

## Arduino libraries that hal shims

Sim builds replace these libraries with hal implementations that keep the same headers and API ([ADR 0002](../../docs/adr/0002-library-shims-over-register-emulation.md)). Pin them in `platformio.ini`:

```ini
lib_deps =
  pololu/VL53L0X@^1.3.1
  madhephaestus/ESP32Servo@^3.2.1
  electroniccats/MPU6050@^1.4.5
```

| Library | For | Notes |
|---|---|---|
| [`pololu/VL53L0X`](https://github.com/pololu/vl53l0x-arduino) 1.3.1 | `sensor.vl53l0x-pololu` | The firmware brings sensors up one at a time with XSHUT and calls `setAddress()`. Drive XSHUT open-drain (it isn't level-shifted). |
| [`madhephaestus/ESP32Servo`](https://github.com/madhephaestus/ESP32Servo) 3.2.1 | `actuator.mg996r`, `actuator.quicrun-1060-540` | 50 Hz by default. `attach(pin)` defaults to 544–2400 µs, so pass `attach(pin, 1000, 2000)` for the ESC. |
| [`electroniccats/MPU6050`](https://github.com/electroniccats/mpu6050) 1.4.5 | `sensor.gy-521-mpu6050` | **Chosen MPU6050 library** (see below). |

**Why `electroniccats/MPU6050`.** It is the i2cdevlib MPU6050 port maintained by Electronic Cats. It has the most GitHub stars of the candidates (471), a release in July 2026, no dependencies, and runs on the ESP32. The alternatives:
- `adafruit/Adafruit MPU6050` is well maintained, but pulls in BusIO, Unified Sensor, GFX and SSD1306.
- `rfetick/MPU6050_light` is stuck at 1.1.0 on the PlatformIO registry.

The shim covers the register-level API: `initialize()`, `testConnection()`, `getMotion6()`, `getAcceleration()`, `getRotation()`, `setFullScaleAccelRange()`, `setFullScaleGyroRange()`, `setDLPFMode()`, `setRate()`. **The DMP path (`dmpInitialize()` and friends) is not supported.** It uploads an undocumented firmware blob to the chip.

## Default catalog

Every value comes from the part's `sources`. Values that aren't published (for example the MG996R pulse range, the Slash steering angle and centre of gravity, and the 540 motor constants at 7.4 V) are estimates, and each part's `notes` says which and why.

Wiring the real car:
- The ESP32 is powered from the 5 V buck. Never use the battery: the DevKitC's 5 V input has only a 10 V capacitor ahead of an LDO. Never use the ESC's BEC either, which is 6 V.
- The VL53L0X breakouts and the MPU6050 are powered from the ESP32's 3V3 pin, so every I²C line idles at 3.3 V.
